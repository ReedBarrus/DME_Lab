# Development Pressure Map v0

This is a derived development-control surface over current DME_Lab repository
standing.

It does not establish empirical claims, scientific resolution, semantic
promotion, or execution authority.

Authoritative scientific standing remains in committed evidence, decisions,
traces, tests, `PROJECT_STATE.md`, and `PRESSURE_RESOLUTION_MAP.md`.

This map exists to keep development search and execution from becoming arbitrary
as persistent Workshop capacity increases.

```text
repository evidence / standing
        |
        v
development pressure map
        |
        v
Council reconstruction / challenge
        |
        v
preflight review
        |
        v
Executive authorization
        |
        v
EXECUTION_PACKET_v0
        |
        v
Workshop
```

The map may expose reachable development pressures.

It does not authorize them.

## Role boundary

### Council

Current interpretive seats:

- SolA — maximal justified compression of shared evidence
- SolB / LabBoiB — minimal boundary against unjustified promotion

Council may:

- reconstruct current development standing;
- identify reachable pressures;
- expose uncertainty, fracture, or unsupported strengthening;
- draft candidate pressure envelopes.

Council does not activate execution.

### Preflight review

A separate reviewer / "Commander" may inspect a candidate packet before
Executive authorization.

The review asks whether the packet is:

- grounded in the declared repository/runtime basis;
- sufficient for Workshop execution;
- free of hidden semantic promotion;
- bounded enough to stop or escalate safely;
- not accidentally prescribing an unsupported architecture or conclusion.

A preflight check is advisory evidence about packet quality.

```text
reviewed packet
!=
authorized packet
```

### Executive

Current Executive: **Reed**.

Only Executive authorization turns a represented packet into an authorized
Workshop handoff.

### Workshop

Current likely Workshop: Astra + Codex.

Workshop may search and execute inside the authorized pressure envelope.

Workshop may not silently widen the pressure or promote semantic standing.

### DP-001 — Shared development pressure surface

- **Pressure:** Can Council, reviewer, Executive, and Workshop all recover the
  same current development reachability from one small derived object without
  converting that object into authority?
- **Standing:** `ACTIVE_CONSTRUCTION`
- **Basis:** current committed repository standing, especially
  `PROJECT_STATE.md`, `PRESSURE_RESOLUTION_MAP.md`, `WORKFLOW.md`, and
  `docs/methods/TWINNING_PROTOCOL_v0.md`
- **Required result:** one derived map that distinguishes:
  - scientific standing;
  - development standing;
  - reachable but unauthorized work;
  - active construction;
  - explicit deferrals.
- **Failure conditions:**
  - the map silently activates a scientific pressure;
  - the map becomes a task queue or scheduler;
  - packet authorization is inferred from reachability;
  - narrative claims outrank repository/runtime evidence;
  - speculative architecture appears as required next work.
- **Resolution criterion:** the object is small enough to reconstruct current
  development reachability and strict enough that the next packet can cite it
  without gaining authority from it.
- **Initial pressure result:** independent reconstruction split between
  `YES` and `UNRESOLVED` on whether map existence already satisfied the
  prior `REACHABLE_AFTER_MAP` wording; one additional response was
  non-admissible because it substituted the scientific PR map for the requested
  development map.
- **Repair verification:** after replacing the ambiguous gate with explicit
  DP-001-resolution semantics, two independent Council observers both returned
  `NO` to whether DP-002 is currently reachable while DP-001 remains
  `ACTIVE_CONSTRUCTION`, and both recovered the same basis relation.
- **Repair standing:** the specific reachability-gate ambiguity is
  **CLOSED_IN_TESTED_SCOPE**. This does not by itself adjudicate all of DP-001
  sufficient.
- **Unlock semantics:** DP-002 becomes reachable for packet formation only
  after DP-001 is explicitly adjudicated sufficient under this resolution
  criterion. Mere existence of `DEVELOPMENT_PRESSURE_MAP.md` does not satisfy
  the unlock.
- **Unlocks:** DP-002

### DP-003 — Independent Workshop recovery of one packet

- **Pressure:** Can two independent Workshop implementations recover the same

- **Standing:** `DEFERRED_UNTIL_REAL_PACKET_EVIDENCE`

## Packet selection rule

The next packet should be selected from a concrete consequential development
ambiguity, not from a desire to exercise the protocol.

A candidate becomes packet-worthy when:

```text
specific unresolved development question
+
recoverable evidence basis
+
bounded Workshop freedom
+
clear evidence debt
+
clear stop / escalation boundary
```

are all present.

Prefer a pressure envelope over a task list.

```text
search freedom inside the envelope
+
hard semantic boundary at the edge
```

## Update rule

Update this map only when repository evidence or explicit Executive action
changes development reachability.

Do not use it as an activity log.

Do not add nodes merely because work could be imagined.

Do not automatically activate the next node after completion.

If this map conflicts with authoritative repository evidence or current
Executive authorization, the evidence or explicit authorization wins.
